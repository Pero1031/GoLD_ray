# GPU

The renderer runs on the CPU. This document is about a second way to run it: **kernel code** that the CPU and the GPU both compile, with checks that the two agree. The CPU renderer stays the reference; features move into the kernel one at a time, each with a check.

**State (2026-11-27): stage 2, conductors, glass, environment maps, spheres, the denoiser's features and clear coats.** A scene file made of quads, spheres and triangle meshes, diffuse surfaces, isotropic rough conductors, smooth and rough glass, clear or tinted coats over a diffuse or a metal base, emitting quads and spheres and an environment (an HDR map or a uniform one) renders on the GPU (`--device gpu`) and, with the same code, on the CPU (`--device cpu-kernel`), also with `--aov` and `--denoise`. The two pictures are the same bits, and both converge to the engine's. 15 of the 56 scene files in `scenes/` render this way. The GGX distribution and the conductor's Fresnel term are one implementation that the engine calls too.

## 1. Design, and where each idea comes from

Before writing code I read how three renderers that run on both devices do it: Mitsuba 3 (with its JIT compiler Dr.Jit), pbrt-v4 and Blender's Cycles. Their sources are cloned (git-ignored) under `references/src/`.

| Decision | GoLD_rayt | Taken from |
|---|---|---|
| One source for both devices | Header-only code under `include/Kernel`, every function marked `RAYT_HD` (`__host__ __device__` under nvcc, nothing under MSVC). No virtual functions, exceptions, heap, std containers or `thread_local` in it. | pbrt-v4 (`PBRT_CPU_GPU`), Cycles (`ccl_device`). Mitsuba reaches the same with a JIT compiler, which is far more machinery than this project needs. |
| The GPU computes in float only | Kernel functions are templates on the scalar type; their double versions exist on the CPU only, and in device code the double overloads are deleted. `build_gpu.ps1` makes ptxas reject any double instruction in the CUDA code and searches the OptiX PTX for one, which catches implicit promotions such as `x * 0.1` with a float `x`. | Cycles builds its CPU kernel with `-Werror=double-promotion`; pbrt-v4 defaults to `Float = float`; Mitsuba always traces in float. |
| The same float bits on both devices | IEEE division and square root and **no implicit fused multiply-adds** (`--fmad=false`; an FMA only where kernel code writes `kfma`). Sine, cosine, atan2 and acos are our own float polynomials (`ksincos`, `katan2`, `kacos`: CEPHES and Dr.Jit's minimax fit, as Dr.Jit implements them), because the library versions differ in the last bits, and CUDA's cosf falls back to double for huge angles (the guard above found it). | Dr.Jit: explicit FMAs and its own transcendental functions, so all of Mitsuba's backends compute the same thing. |
| Fast math as an option | `build_gpu.ps1 -FastMath`. Accurate enough, but no longer bit-identical to the CPU, and only 5 % faster on the test scene (section 3). | pbrt-v4 and Cycles build their GPU code with `--use_fast_math`. |
| CUDA is optional | The GPU code is a separate DLL, `GoLD_rayt_gpu.dll`, loaded at run time (`Gpu/GpuDevice.hpp`). The CLI builds and runs without CUDA; GPU checks print SKIP. A module of another interface version is refused. OptiX comes with the driver; only its headers are needed to build. | Mitsuba and Cycles load the CUDA / OptiX driver at run time; Mitsuba's tests skip missing devices. |
| Random numbers | A PCG32 stream per camera path, keyed by (run seed, pixel, sample) only (`Kernel/Rng.hpp`). The engine's `thread_local` Mersenne Twister cannot run on a GPU. | Cycles (`path_rng_1D`), pbrt-v4 (stateless samplers). |
| The scene | Flat arrays of plain numbers (`Kernel/KernelScene.hpp`), built from the scene file's description (`Cli/KernelScenePack`), not from the engine's objects. Materials are plain data with a type, chosen by a branch, not virtual classes. | Cycles (`KernelData` and flat arrays, closure structs with a `switch`), pbrt-v4 (`TaggedPointer`). |
| Integrator | A megakernel: one OptiX ray-generation program runs a whole camera path (`kernel::tracePath`, the same function the CPU runs); the closest-hit program only reports the hit; one launch per sample adds that sample of every pixel to a sum, so launches stay short and the sums are added in the CPU's order. | Mitsuba (megakernel by default, no shading in hit programs); Cycles runs the same per-path state machine on the CPU. |
| Hit points | Only the triangle is taken from the tracer (Embree on the CPU, OptiX on the GPU); the kernel recomputes the hit point with its own formula, and moves ray origins off surfaces in integer steps of the float representation (Wächter and Binder, Ray Tracing Gems ch. 6). | Cycles re-intersects the triangle to get a hit point it controls, and uses the same integer offset. |
| Spheres | An analytic primitive with one intersection function, `kernel::intersectSphere` (Haines et al., Ray Tracing Gems ch. 7), which Embree calls as user geometry and OptiX as the intersection program of a custom primitive, so both tracers report the same distance; the kernel puts the point back on the sphere. On the GPU the triangles and the spheres are two acceleration structures under an instance one (identity transforms; a scene without spheres keeps the single triangle structure). | Mitsuba binds the same routine to Embree's user geometry and OptiX's custom primitives; pbrt-v4 re-projects sphere hits onto the surface. |
| Layered materials | `Kernel/Layered.hpp` repeats the engine's `LayeredCoat` step by step: a rough dielectric coat (its own GGX, with pbrt-v4's sampling of the visible normals) over a Lambertian or the kernel's rough conductor, the light between them summed by random walks with next-event estimation at both layers, Beer-Lambert in a tinted coat (`kexp`: CEPHES's exp in float, as Dr.Jit has it). The walks draw from the path's stream through a small source (one number, or two), which the check binds to the engine's stream instead. `LayeredCoat` now draws each number on its own line (an argument list leaves the order to the compiler); its renders stayed the same bits. The path tracer chooses its light first and evaluates the BSDF in one place, so the GPU program holds one copy of the walk. | pbrt-v4's `LayeredBxDF` (Jakob et al. 2014; Guo et al. 2018), which runs on its GPU too; it seeds a generator from a hash of the directions inside `f()`, where this kernel passes the path's stream. |
| Denoiser features | The kernel records the albedo and the shading normal by the engine's rule (`PathIntegrator::Li`): at the first vertex whose material is not specular, emitters included, or the environment's color if the path leaves before one; averaged over the samples, a sample without features adding zero. Each material's albedo and whether it is specular are read from the engine's object (`Material::aovAlbedo`, `isSpecular`), and recording draws no random number, so the picture is the same bits with or without. The denoiser is the engine's: Intel OIDN on the CPU, run on the kernel's picture and features (`Render/Denoiser.hpp`). | Cycles writes its denoising albedo and normal at the first bounce that is not close to specular; Cycles offers OIDN and the OptiX denoiser, Mitsuba 3 the OptiX one. |
| Tests | A ladder, section 2. | Mitsuba (`test_renders.py`: per-pixel z-test against a CPU reference), and this project's Mitsuba comparison (`MITSUBA_CHECK.md`). |

What the kernel renderer models: quads, spheres, triangle meshes (OBJ / PLY / STL, with their transform) and lathes; diffuse surfaces with a constant albedo (smooth vertex normals as the engine uses them); isotropic rough conductors with the Kulla-Conty lobe; dielectrics, smooth (delta reflection and refraction) or rough (GGX reflection and transmission), also against water (`Kernel/Materials.hpp`); clear or tinted coats over a constant diffuse or an isotropic rough conductor (`Kernel/Layered.hpp`; a textured base, an anisotropic or glinting base metal are refused); emitting quads and spheres, one- or two-sided, sampled by next-event estimation (chosen by power; a uniform point on a quad, the cone a sphere subtends as the engine's `Sphere::sampleFrom`, `Kernel/Lights.hpp`) with the power heuristic against BSDF sampling; an environment map, HDR or uniform (the engine's EnvMap: equirectangular, bilinear, importance-sampled by luminance x sin(theta); a light sample picks it by power against the other lights, as pbrt's PowerLightSampler weighs an infinite light, `Kernel/Environment.hpp`); a pinhole camera; the engine's path depth and Russian roulette; the denoiser's features (`--aov`, `--denoise`); the RGB build. Anything else in a scene file or on the command line is refused with a list of what is missing (for example point lights, dispersion or a medium inside glass, an anisotropic or glinting conductor, `--stokes`); `--device cpu` renders it.

How a material moves into the kernel (stage 2): the physics that both need goes into a kernel header as templates on the scalar type, in the engine's order of operations, and the engine calls it (`Kernel/Microfacet.hpp`: GGX D, Smith Lambda, sampling of the visible normals, the conductor's Fresnel term; `Microfacet/GGX.cpp` and `fresnel::fresnelConductor` now call these). The engine's renders of conductor scenes stayed the same bits (gold, anisotropic, multiple-bounce and glint spheres; RGB and spectral). The kernel's material (`Kernel/Materials.hpp`) repeats the engine class's steps for the case it models and takes its parameters from the engine's object (`RoughConductor::kernelParams`: the RGB index the engine derived from the metal's table, alpha, the Kulla-Conty table row), so nothing is derived twice. The dielectric works the same way (`Dielectric::kernelParams`: the relative index, alpha, smooth or not); for it the path tracer learned delta events (no light sample at a smooth surface; the throughput takes the event's weight, as `PathIntegrator::updateThroughput`) and refraction (a refracted ray leaves from the other side of the surface; a light sample may lie behind a rough surface). The environment is read from the engine's EnvLight too (its map, its Distribution2D, which the engine already keeps in float, and its scale; `EnvMap::image`, `EnvMap::distribution`), and `Kernel/Environment.hpp` repeats EnvMap's lookup, sampling and density. The coat comes from `LayeredCoat::kernelParams` (the coat's index and alpha, its optical depth per channel, the walks; the base's reflectance or the base conductor's parameters, which the engine built with the coat as the incident medium).

## 2. Checks

`--scene gpu` (both builds; the GPU parts print SKIP without the module or a device):

1. **Kernel = engine, on the CPU in double.** Each kernel sampling function mirrors an engine function (same formula, same order of operations), so their doubles must be the same bits: cosine-weighted hemisphere, uniform sphere, orthonormal basis, dielectric Fresnel; 4096 cases with edges. All bit-identical.
2. **White furnace, kernel renderer on the CPU**: `scenes/gpu_box.json` with every albedo 1 and no lamp in a uniform environment of radiance 1, where every pixel converges to 1. Mean 0.99775 ± 0.0009 (since the environment became a sampled light; −2.5 standard errors, and 1.00002 ± 0.00011 over four seeds of 1024 spp, so chance).
3. **Random numbers, GPU = CPU, bit for bit.**
4. **Floats, GPU = CPU, bit for bit**, per function (exp included): 100 % identical on a Quadro M4000. (With `-FastMath`: the GPU's floats must be as close to the double reference as the CPU's; they are, 61 to 84 % bit-identical.)
5. **White furnace on the GPU**: the same bits as on the CPU.
6. **The test scenes on the CPU kernel and on the GPU with the same seed: the same bits** in every pixel, the albedo and normal features included, `scenes/gpu_box.json`, `scenes/gpu_metals.json`, `scenes/gpu_glass.json`, `scenes/gpu_env.json`, `scenes/gpu_spheres.json` and `scenes/gpu_coat.json` (`-FastMath`: the same mean within the noise); and a render without the features is the same picture.
7. **The kernel's conductor in double = the engine's RoughConductor**, eval, pdf and sample on 4096 direction pairs (shading normals tilted from the geometric ones, half of the pairs near the mirror direction), for rough gold with the Kulla-Conty lobe, smooth gold, and rough gold without the lobe: 100 % bit-identical.
8. **The kernel's dielectric in double = the engine's Dielectric**, the same way, for smooth glass, rough glass (alpha 0.09) and rough glass in water (relative index 1.125), entering and leaving, with a third of the pairs near the refracted direction: 100 % bit-identical. A rough surface's choice between reflection and refraction is drawn inside `Dielectric::sample` from the engine's own stream; the check seeds that stream, reads the number the engine will draw, seeds it again, and hands the same number to the kernel.
9. **Each material in float, GPU = CPU, bit for bit** (diffuse, the three conductors, the three dielectrics, the four coats of `scenes/gpu_coat.json`; eval, pdf and sample, a coat's walks from a stream per case): 100 %.
10. **The kernel's environment = the engine's EnvMap** (the mapping in double, as the engine): eval, pdf and sample on 4096 directions (a tenth within a degree of a pole) and sample pairs, for the uniform map and a 2048 x 1024 HDR: 100 % bit-identical. The float atan2 and acos, GPU = CPU bit for bit (largest difference from the double ones 7.1e-7).
11. **The tracers agree:** every ray a CPU path trace of the six test scenes casts (about 60 000 each, closest-hit and shadow) is traced again by OptiX: the same primitive, for a sphere the same distance, the same blocked shadow rays, everywhere (at most 1e-4 of the rays may differ). Since the kernel takes only these from the tracer, this is the only place where the devices' paths could part.
12. **The kernel's sphere light in double = the engine's Sphere** (`sampleFrom` with `AreaLight::sampleLi`'s direction, and `pdfSurface`), for a small sphere far away, a middle one and a large one, from 4096 points, a fifth of them inside the sphere (where both sample a uniform point of the surface): 100 % bit-identical.
13. **The denoiser's features on the same rays as the engine**: one ray through the centre of each pixel of a 64 x 48 grid, followed by the kernel (`kernel::traceRay`, float) and by the engine (`PathIntegrator::Li` with a `PathAOV`), in the six test scenes. Rays whose first surface is smooth glass are left out (60 and 108 of 3072), since both renderers choose reflection or refraction there at random; every other ray records its features at its first surface or at the environment. None differs (1 in 500 would be allowed, for edges the two tracers settle differently); surfaces agree within 3e-8 (albedo) and 8.6e-6 (normal), the environment's color within 4.3e-5: the kernel maps the direction to the HDR in float, which moves the bilinear lookup by about 3e-5 of a texel (allowed: 1e-3).
14. **The kernel's coat in double = the engine's LayeredCoat**, for the four coats of `scenes/gpu_coat.json` as the engine builds them from the scene file (a smooth coat over red, a clear coat over gold, an amber-tinted coat, a satin coat with two walks): eval, pdf and sample on 2048 direction pairs, with the engine's stream seeded before the engine's call and again before the kernel's, which draws the same numbers in the same order: 100 % bit-identical (a random walk of up to 12 bounces per evaluation, each a few dozen operations: one rounding difference would show).

The tracer check found the one way they did part: the first glass scene had its vase standing exactly in the floor's plane. Rays inside the glass then hit two coincident surfaces at the same distance, and Embree and OptiX settled the tie differently (both rightly): 83 of 38 000 rays, 2.5 % of the pixels not bit-identical, and a mean 0.1 % off at 8 spp. With the floor 1 mm lower, every pixel is the same bits. Coincident surfaces are ambiguous for any renderer; the engine settles them a third way.

What is left is a ray through the edge two triangles share. Both tracers are watertight, but they give such a ray to different triangles when it passes within a few millionths of the edge; the kernel then recomputes the hit on the other triangle, so the point and the interpolated normal differ in the last bits. At full size (`scenes/gpu_env.json`, 400 x 300, 16 spp: 4 677 889 rays) this happened once (2.6e-6 from the edge in barycentrics), and one pixel channel differed by one unit in the last place (6e-8). It cannot be avoided while the two devices use different tracers; the checks at 128 x 96 see none. A relative of it: a hit point exactly on the line where two walls meet (the floor's edge under a wall) is offset along the floor's normal only, so the next ray starts in the wall's plane, and the tracers disagree whether the wall at distance 0 blocks it. At full size (`scenes/gpu_spheres.json`, 400 x 300, 16 spp: 9 600 279 rays, 801 253 of them hitting spheres) this was the only difference: one shadow ray, one pixel off by 4.5e-4; every sphere hit had the same sphere and the same distance on both devices.

A fixed tolerance on |GPU − CPU| in float would be the wrong test: just past the critical angle (glass to air, cos θ 0.7458 against a critical 0.7454) the Fresnel term takes the square root of a small number, which turns a rounding difference in its input into 1.4e-5 in its output. With the same operations on both devices the difference is zero instead.

## 3. Speed

`scenes/gpu_box.json` (780 triangles), 400 × 300, 256 spp, depth 16, on this PC (i7-6700K, 8 threads; Quadro M4000, Maxwell, no RT cores):

| Renderer | Render time |
|---|---|
| engine, `--device cpu` (double, every feature) | 18.2 s |
| kernel on the CPU, `--device cpu-kernel` (float, Embree) | 4.4 s |
| kernel on the GPU, `--device gpu` | 2.2 s (+ 0.3 s to set up OptiX) |
| kernel on the GPU, built with `-FastMath` | 2.1 s |

The GPU is twice as fast as the same kernel on the CPU here; the larger step from the engine to the kernel comes from float and from the much smaller set of features a path has to check. Fast math hardly helps: the time goes into ray traversal and memory, not arithmetic, so the bit-exact default costs about 5 %. A GPU with RT cores traverses rays in hardware; the ratio will look different there.

A real scene: `scenes/erato_gold.json` (the scanned statue, 412 498 triangles, in gold under three lamps), 600 × 800, 256 spp, denoised: the whole program takes 81 s with the engine, 31 s with the kernel on the CPU (22 s of it rendering) and 27 s on the GPU (18 s rendering); OIDN adds 0.4 s. On a large mesh this card without RT cores is hardly faster than Embree on four cores.

Coats are the GPU's weak case on this card. `scenes/gpu_coat.json` at 64 spp renders in 2.5 s on the CPU kernel and 5.7 s on the GPU (1.35 M samples per second against 3.1 M): every coat evaluation is a random walk whose length varies from thread to thread, so the threads of a warp wait for the longest. Two quick remedies made things worse and were dropped: keeping the walk out of line (`__noinline__`: the coat scene unchanged, the conductor scene 40 % slower) and allowing 255 registers (both slower: fewer threads per multiprocessor). Sorting the paths by material between bounces (a wavefront integrator) is the known remedy.

(These times are stage 1's. The same scene at the same settings now takes 3.0 s on the GPU without its environment and 4.8 s with it: the larger kernel (more materials) costs 15 %, and the environment 60 %, as every ray that leaves the open box looks the map up and computes its density for the weights (atan2, acos, sin, cos and a bilinear lookup, in float). Speed is not the aim on this card; a wavefront integrator or RT cores would change these numbers.)

## 4. Build and run

```
powershell -ExecutionPolicy Bypass -File tools\build_cli.ps1 -Dev      # the CLI (no CUDA needed)
powershell -ExecutionPolicy Bypass -File tools\build_gpu.ps1           # GoLD_rayt_gpu.dll next to it (about 10 s)
cd GoLD_rayt
..\out\cli-dev\GoLD_rayt.exe --scene gpu
..\out\cli-dev\GoLD_rayt.exe scenes\gpu_box.json --device gpu
```

Each output folder needs its own module: `build_gpu.ps1 -OutDir out\cli-dev-spectral` for the spectral build (whose checks otherwise SKIP the GPU part, with the module's interface version as the reason). `build_gpu.ps1 -Arch 75,86,89` compiles machine code for other GPUs; `-FastMath` as above. PTX (the GPU's intermediate code) of the lowest architecture is always embedded, so a newer GPU runs the module too: its driver compiles the PTX on the first launch. The design is not tied to the current card. Recent Mitsuba already requires compute capability 7.5 (Turing) or newer, and CUDA 13 no longer compiles for Maxwell, so a Maxwell card like the M4000 needs CUDA 12.x. The OptiX SDK headers are found in `OPTIX_ROOT` (default: OptiX SDK 8.1.0).

Files: `include/Kernel/` (shared code: `HostDevice`, `KernelMath`, `Rng`, `Sampling`, `Microfacet`, `Materials`, `Layered`, `Bsdf` (the materials by type), `Environment`, `Lights`, `KernelScene`, `PathTracer`, `SelfTest`), `include/Gpu/` (the module's interface and loader), `GoLD_rayt/gpu/` (the module: `GpuModule.cu` CUDA, `OptixRender.cpp` OptiX host code, `OptixPrograms.cu` the OptiX programs), `src/Cli/KernelScenePack.cpp` (scene file to kernel scene, the CPU kernel renderer, `--device`), `src/Cli/Checks/GpuChecks.cpp`, `tools/build_gpu.ps1`, `tools/test/gpu_compare.py` (against the engine), `tools/test/pfm_compare.py` (two PFM pictures pixel by pixel).

Writing kernel code: float constants as `T(0.1)`, never bare double literals (the build stops otherwise); `kfma` where a fused multiply-add is wanted; `ksin` / `kcos` / `ksincos` instead of the library's.
